# A2A — Agent-to-Agent Protocol

🔥🔥🔥 Interview weight — explicitly asked in senior AI engineer interviews. Prerequisites: [Multi-Agent Systems](./06-multi-agent), [MCP](./07-mcp).

## 🗣️ In Plain English

::: tip In Plain English
Imagine your company has several departments — legal, finance, engineering — each run by a department head. When the engineering lead needs a legal opinion, they don't walk into the legal office and start rummaging through files themselves. They send a formal request: *"I need a contract reviewed. Here's the document. Please confirm when it's done and send back your findings."*

The legal department head receives that request, assigns it to the right person, works on it, and sends back a structured response. The engineering lead doesn't know or care who inside legal did the work. They just know they sent a request to a capable department and got a result back.

That's A2A. When one AI agent needs help from another AI agent, A2A is the formal protocol they use to make that request — including how they find each other, how they agree on what to do, how they track progress, and how they handle failures. Without it, agents talking to each other would be like people yelling across a building with no agreed language or process.

The key insight: **MCP is how an agent talks to tools and data. A2A is how an agent talks to another agent.** Tools are passive — they wait to be called. Agents are active — they reason, plan, and push back.
:::

## ⚙️ Under the Hood

A2A (Agent-to-Agent) is an open protocol published by Google in 2025, designed to standardize communication between AI agents across different frameworks, vendors, and runtime environments.

### The core problem A2A solves

In a multi-agent system without A2A, agents communicate through whatever ad-hoc mechanism the developer wired up — direct function calls, custom REST endpoints, shared database state. This works inside a single codebase but breaks immediately when:

- Agent A is built with LangGraph and Agent B is built with AutoGen
- Agent A runs in your cloud and Agent B is a third-party service
- Agent B is an async, long-running task that won't finish immediately
- You need to authenticate and authorize inter-agent communication
- You need to audit which agent instructed which other agent to do what

A2A solves all of this with a standard protocol.

### The Agent Card

Every A2A-capable agent publishes an **Agent Card** — a JSON document (typically at `/.well-known/agent.json`) describing what it can do:

```json
{
  "name": "RiskAnalysisAgent",
  "description": "Evaluates trade risk and returns VaR estimates",
  "url": "https://risk-agent.internal/a2a",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true
  },
  "skills": [
    {
      "id": "evaluate_trade_risk",
      "name": "Evaluate Trade Risk",
      "description": "Given a proposed trade, returns risk metrics including VaR, CVaR, and position limits",
      "inputModes": ["application/json"],
      "outputModes": ["application/json"]
    }
  ],
  "authentication": {
    "schemes": ["Bearer"]
  }
}
```

An orchestrator agent discovers available agents by reading their cards — either from a registry or a known set of URLs. This is **agent discovery**: the equivalent of DNS for agents.

### The Task lifecycle

A2A communication is modelled as **Tasks**, not simple request/response calls. This matters because agents do non-trivial work that takes time.

```
Client Agent                              Server Agent
     │                                         │
     │──── POST /tasks/send ──────────────────►│  Create task
     │◄─── { taskId, status: "submitted" } ────│
     │                                         │  (agent is working...)
     │──── GET /tasks/{taskId} ───────────────►│  Poll status
     │◄─── { status: "working" } ──────────────│
     │                                         │  (agent finishes)
     │──── GET /tasks/{taskId} ───────────────►│
     │◄─── { status: "completed", result } ────│
```

Task states:

| State | Meaning |
|-------|---------|
| `submitted` | Task received, not yet started |
| `working` | Agent is actively processing |
| `input-required` | Agent needs more info (human-in-the-loop gate) |
| `completed` | Done — result attached |
| `failed` | Terminal failure with error detail |
| `canceled` | Canceled by client |

The `input-required` state is important: an agent can pause mid-task and request clarification, either from the calling agent or from a human. This is how human-in-the-loop approval gates work in A2A.

### Streaming responses

For long-running or progressive tasks (like an agent streaming its reasoning steps), A2A supports **Server-Sent Events**:

```typescript
// Client subscribes to task updates
const response = await fetch(`${agentUrl}/tasks/sendSubscribe`, {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    id: crypto.randomUUID(),
    message: {
      role: 'user',
      parts: [{ type: 'text', text: 'Analyze EURUSD exposure for portfolio ID 4821' }]
    }
  })
})

const reader = response.body!.getReader()
const decoder = new TextDecoder()

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  const chunk = decoder.decode(value)
  // Each chunk is a TaskStatusUpdateEvent or TaskArtifactUpdateEvent
  const event = JSON.parse(chunk.replace('data: ', ''))
  console.log(event.status, event.artifact)
}
```

### Authentication and authorization

A2A agents authenticate each other using standard mechanisms — Bearer tokens (JWT), OAuth 2.0, or API keys. The Agent Card declares which schemes are supported.

A critical security property: **the calling agent's identity is preserved in the task context**. If Orchestrator Agent (authenticated as `orchestrator@company.com`) asks Risk Agent to evaluate a trade, the Risk Agent knows who asked. This supports audit trails and fine-grained authorization — the Risk Agent can check whether this orchestrator is allowed to request evaluations for this portfolio.

### A2A vs MCP — the definitive distinction

| | MCP | A2A |
|---|---|---|
| **What connects** | Agent ↔ Tool/Data source | Agent ↔ Agent |
| **Other side is** | Passive (waits to be called) | Active (reasons, plans, can refuse) |
| **Communication model** | Request/response | Task lifecycle (async, stateful) |
| **Discovery** | MCP server manifest | Agent Card at `/.well-known/agent.json` |
| **Output** | Structured data | Could be text, data, or another task delegation |
| **Pushback possible?** | No — tools execute or error | Yes — agent can request input, negotiate |
| **Example** | Agent calls a database query tool | Orchestrator delegates to Risk Analysis Agent |

The practical rule: if the other side has an LLM making decisions, use A2A. If the other side is a function that executes deterministically, use MCP.

### Full orchestration example

```typescript
// Orchestrator agent delegates to two specialist agents in parallel
// run: npx ts-node orchestrator.ts

interface A2ATask {
  id: string
  message: { role: string; parts: Array<{ type: string; text: string }> }
}

interface TaskResult {
  status: string
  artifacts?: Array<{ parts: Array<{ type: string; text: string }> }>
}

async function sendTask(agentUrl: string, text: string, token: string): Promise<string> {
  const taskId = crypto.randomUUID()

  // Submit task
  await fetch(`${agentUrl}/tasks/send`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${token}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      id: taskId,
      message: { role: 'user', parts: [{ type: 'text', text }] }
    } satisfies A2ATask)
  })

  // Poll until complete (production: use webhooks instead)
  while (true) {
    const res = await fetch(`${agentUrl}/tasks/${taskId}`, {
      headers: { 'Authorization': `Bearer ${token}` }
    })
    const task: TaskResult = await res.json()

    if (task.status === 'completed') {
      return task.artifacts?.[0]?.parts?.[0]?.text ?? ''
    }
    if (task.status === 'failed') throw new Error(`Task ${taskId} failed`)
    await new Promise(r => setTimeout(r, 500)) // back off
  }
}

async function orchestrate(tradeProposal: string) {
  const token = process.env.INTERNAL_AGENT_TOKEN!

  // Delegate to specialists in parallel
  const [riskResult, complianceResult] = await Promise.all([
    sendTask('https://risk-agent.internal/a2a', tradeProposal, token),
    sendTask('https://compliance-agent.internal/a2a', tradeProposal, token),
  ])

  // Synthesize results
  return { risk: riskResult, compliance: complianceResult }
}
```

## 💥 Where It Bites (Production Lens)

::: warning Where It Bites

**Polling loops hammering downstream agents.** Naive implementations poll `/tasks/{id}` every 500ms. At scale with thousands of in-flight tasks, this creates a thundering herd on downstream agents. Fix: implement webhook/push notification support — A2A's `pushNotifications` capability lets the server agent POST updates to a callback URL instead of waiting to be polled.

**No circuit breaker on agent-to-agent calls.** If the Risk Agent is slow or down, the Orchestrator blocks all trades waiting for it. Symptom: cascading latency, queue depth growing, eventual OOM on the orchestrator. Fix: treat every A2A call like an external HTTP call — timeouts, retries with exponential backoff, circuit breakers. Task state `failed` after timeout, not a hung task forever.

**Identity confusion in audit logs.** Multi-hop delegation (Orchestrator → Portfolio Agent → Risk Agent) loses the original requester's identity unless you explicitly propagate it. Two weeks later, your audit log says "Risk Agent requested this evaluation" with no trace of who told Portfolio Agent to do it. Fix: thread a correlation ID and the original user identity through all task submissions as metadata.

**Treating A2A agents like synchronous functions.** Developers expect `await sendTask(...)` to return in milliseconds. A2A tasks are async by design — the agent on the other side might take 30 seconds reasoning through a complex problem. Design calling code for long polling or webhooks from the start; retrofitting async onto synchronous assumptions is painful.

:::

## 🎯 Checkpoint

::: details Question 1 — A2A vs MCP: when do you use each?
**Q:** Your orchestrator agent needs to (a) look up a customer's account balance from your database, and (b) get a risk assessment from a specialist AI agent. Which protocol do you use for each, and why?

**A:** (a) Database lookup → **MCP**. The database is a passive data source — it executes queries deterministically and returns data. You build an MCP server that exposes `get_account_balance` as a tool. The agent calls it, gets the result. No reasoning on the other side.

(b) Risk assessment → **A2A**. The risk assessment agent has its own LLM, its own reasoning process, and may take variable time depending on trade complexity. It might need to call its own tools (MCP), spawn sub-tasks, or request clarification. That's an active agent, not a passive tool. A2A handles the async task lifecycle, authentication, and result delivery.

The line is: does the other side *reason*? If yes, A2A. If it just executes, MCP.
:::

::: details Question 2 — What is an Agent Card and why does it matter?
**Q:** Explain what an Agent Card is in the A2A protocol and what problem it solves.

**A:** An Agent Card is a JSON document published at a well-known URL (`/.well-known/agent.json`) that describes an agent's identity, capabilities, skills, supported input/output modes, and authentication requirements. It's the mechanism for **agent discovery** — how orchestrators find out what agents exist and what they can do, without hard-coding that knowledge.

Without Agent Cards, you'd need to manually configure every orchestrator with every downstream agent's API contract — brittle, un-discoverable, and unmaintainable as the agent ecosystem grows. Agent Cards make the ecosystem self-describing: a new agent registers itself by publishing its card; any A2A-compatible orchestrator can discover and use it by reading the card. This is the same principle as OpenAPI specs for REST APIs, but applied to agent capabilities.
:::

## Key Mental Models

**A2A is the protocol for agents talking to agents; MCP is the protocol for agents talking to tools.** Never conflate them — the distinction is whether the other side reasons.

**A2A models work as Tasks, not calls.** Tasks have a lifecycle (submitted → working → completed/failed) because agents do real work that takes time. Design for async from the start.

**Agent Cards enable discovery.** An agent that publishes a card can be found and used by any A2A orchestrator without prior coordination.

**Identity and audit trails must be explicitly threaded.** Multi-hop agent calls lose the original requester unless you propagate it as task metadata at every hop.

**The `input-required` state is where human-in-the-loop gates live.** An agent can pause and wait for human approval mid-task — this is A2A's native mechanism for keeping humans in the loop on consequential decisions.
