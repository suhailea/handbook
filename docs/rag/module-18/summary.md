## What You Learned in Module 18

**Case Studies** — you studied 10 end-to-end RAG designs and, more importantly, learned when RAG is the *wrong* tool:
- Real-time data (flight status, stock prices) needs live APIs, not embeddings.
- Tabular data (CSV analytics) needs SQL, not vector search.
- Structured data (e-commerce products) needs hard filters before semantic search.
- Tool-heavy workflows (booking assistants) are orchestration problems, not retrieval problems.

**Reference Implementation** — you saw the concrete code for each stage of the pipeline: parse, chunk, embed, store, search (hybrid), rerank, construct context, generate (streaming with citations), and cache. The key architectural decisions:
- ACL as a database pre-filter, always.
- RRF fusion of vector + keyword search as the default retrieval strategy.
- Citation IDs assigned during context construction, not generated by the LLM.
- Cache keys that include the access context, not just the query.

**Production Checklist** — you have 100+ actionable items across 30 categories. The essential principle: security and evaluation are launch blockers; everything else is a post-launch optimization.

## Mental Models from the Entire RAG Track

These are the ideas that should stay with you long after the details fade:

1. **RAG is retrieval, not magic.** The quality of your answers is bounded by the quality of your retrieved chunks. Invest in retrieval before investing in fancier LLMs.

2. **Chunking is the foundation.** Bad chunks propagate errors through the entire pipeline — bad embeddings, bad retrieval, bad answers. Get chunking right first.

3. **Hybrid search is the production default.** Pure vector search misses exact matches. Pure keyword search misses semantic similarity. Use both, fuse with RRF.

4. **ACL is a pre-filter, never a post-filter.** Unauthorized chunks must never leave the database, even temporarily.

5. **Not everything is a RAG problem.** Real-time data needs APIs. Structured data needs SQL. Know when to reach for a different tool.

6. **Evaluation is not optional.** Without a golden test set and automated metrics, you are deploying blind. Retrieval recall, answer faithfulness, and citation accuracy are the three metrics that matter most.

7. **The hard problems are parsing and chunking, not generation.** The LLM is the easy part. Getting clean, well-structured, well-chunked content into the vector database is where most of the engineering effort belongs.

8. **Every external API will fail.** Embedding services, LLM providers, rerankers, vector databases — build retry logic, circuit breakers, and graceful degradation for every one of them.

9. **Freshness is a design choice, not an afterthought.** Decide your staleness budget up front and build the ingestion pipeline around it.

10. **Security in RAG is multi-layered.** ACL filtering, prompt injection defense, PII scrubbing, output guardrails, and audit logging — you need all of them, not just one.
