# L4 vs L7 & Algorithms

<Badge type="tip" text="Interview: 🔥🔥🔥🔥" /> <Badge type="info" text="Prereqs: TCP/IP basics, HTTP fundamentals" />

## 🗣️ In Plain English

::: tip In Plain English
Imagine you work at the front desk of a huge hotel with dozens of concierge agents behind you. Your job is to send each arriving guest to a concierge who can help them.

**Layer 4 load balancing** is like glancing at the guest's room key card -- you see a room number (port) and the building they came from (IP address), but you have no idea what they actually need. You pick a concierge quickly, hand the guest off, and move on. You never open their luggage or read their request form. It is fast and simple, but you cannot make smart routing decisions because you are deliberately ignorant of the guest's actual question.

**Layer 7 load balancing** is like reading the guest's request form before routing them. "Oh, you need the spa? Go to concierge 3 -- she handles all wellness requests." "You want to check out? Concierge 7 handles billing." Because you understand the content of the request, you can route more intelligently: send API traffic to one pool of servers, static assets to another, and admin requests to a locked-down third pool. The trade-off is that reading each form takes a bit longer than just glancing at a room key.

Now, once you decide *which* concierge to send the guest to, you need a *strategy* for choosing. Do you go in order (round-robin)? Pick the concierge who currently has the fewest guests (least connections)? Always send returning guests to the same person (sticky sessions)? Each strategy -- each *algorithm* -- has strengths and weaknesses, and the best choice depends on whether your guests' requests are quick questions or hour-long planning sessions.

The rest of this page digs into exactly when to use L4 vs L7, the algorithms you will encounter in interviews and production, health checking, TLS termination, and the sticky-sessions debate.
:::

## ⚙️ Under the Hood

### L4 vs L7: What Each Layer Sees

| Property | L4 (Transport) | L7 (Application) |
|---|---|---|
| **OSI Layer** | 4 -- TCP / UDP | 7 -- HTTP, gRPC, WebSocket |
| **Visible data** | Source/dest IP, source/dest port, TCP flags | Full HTTP request: URL, headers, cookies, body |
| **Can route by URL path?** | No | Yes |
| **Can modify request/response?** | No (pass-through) | Yes (rewrite headers, inject cookies, redirect) |
| **TLS handling** | Pass-through (or terminate) | Typically terminates TLS |
| **Performance** | Higher throughput, lower latency | Slightly more overhead per request |
| **Connection multiplexing** | One upstream conn per client conn | Can multiplex many client conns over fewer upstream conns |
| **Health checks** | TCP connect / UDP ping | HTTP `GET /health` with status code validation |
| **Examples** | AWS NLB, HAProxy (TCP mode), LVS | nginx, AWS ALB, Envoy, HAProxy (HTTP mode), Traefik |

### When to Use Which

| Scenario | Recommended | Why |
|---|---|---|
| Raw TCP services (databases, message brokers) | L4 | No HTTP to inspect |
| Need path-based routing (`/api` vs `/static`) | L7 | Must read the URL |
| Extreme throughput, minimal latency | L4 | Less processing per packet |
| A/B testing, canary deploys by header/cookie | L7 | Must inspect application data |
| WebSocket or gRPC with path routing | L7 | Need `Upgrade` header handling and path awareness |
| Non-HTTP protocols over TCP | L4 | L7 does not understand arbitrary protocols |
| TLS pass-through (end-to-end encryption to backend) | L4 | L4 forwards encrypted bytes without decrypting |

### Load Balancing Algorithms

#### Round-Robin

Each server gets the next request in rotation: server 1, server 2, server 3, server 1, ...

- Simple and predictable.
- Fair only when all requests take roughly the same time and all servers have the same capacity.
- Ignores current server load entirely.

#### Weighted Round-Robin

Same rotation, but servers with higher weights receive proportionally more requests. A server with weight 3 gets three requests for every one that a weight-1 server receives.

```nginx
upstream backend {
    server 10.0.0.1:3000 weight=3;   # 3x traffic
    server 10.0.0.2:3000 weight=1;   # 1x traffic
}
```

Use when servers have different CPU/memory capacities.

#### Least Connections

Route each new request to whichever server currently has the fewest active connections.

- Excellent for workloads with variable request duration (some fast, some slow).
- Naturally adapts: a slow server accumulates connections and stops receiving new ones.
- Most load balancers support `least_conn` with weights (`weighted least connections`).

```nginx
upstream backend {
    least_conn;
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
}
```

#### IP Hash

Hash the client's IP address to deterministically map it to a server. The same client IP always reaches the same backend.

- Provides natural session affinity without cookies.
- Problem: clients behind a corporate NAT or CDN share one IP, creating hot spots.
- Adding or removing servers reshuffles most mappings (see consistent hashing below).

```nginx
upstream backend {
    ip_hash;
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
}
```

#### Consistent Hashing

A hash ring maps both servers and request keys (e.g., user ID, cache key) onto a circle. Each request routes to the nearest server clockwise on the ring.

- When a server is added or removed, only ~1/n of keys are remapped (versus nearly all keys with simple modular hashing).
- Critical for cache-friendly routing: keeps cache hit rates high during scaling events.
- Virtual nodes (vnodes) improve uniformity -- each physical server gets multiple points on the ring.

```nginx
upstream backend {
    hash $request_uri consistent;
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
}
```

#### Random with Two Choices (Power of Two Choices)

Pick two servers at random, then send the request to whichever has fewer active connections.

- Surprisingly effective: reduces maximum load from O(log n / log log n) to O(log log n).
- Avoids the thundering-herd problem that least-connections can have when many load balancers query the same "least loaded" server simultaneously.
- Used internally by Envoy and other modern proxies.

### Health Checks

| Type | How It Works | Pros | Cons |
|---|---|---|---|
| **Active -- TCP** | LB opens a TCP connection to the backend port periodically | Simple, protocol-agnostic | Backend port open does not mean app is healthy |
| **Active -- HTTP** | LB sends `GET /health` and checks for 200 | Validates application readiness | Slightly more overhead |
| **Passive** | LB monitors real traffic; marks backend unhealthy after N consecutive errors | No extra traffic | Slow to detect failures if traffic is low |

Key parameters:
- **Interval:** how often to probe (e.g., every 5 seconds).
- **Timeout:** how long to wait for a response (e.g., 3 seconds).
- **Unhealthy threshold:** consecutive failures before marking down (e.g., 3).
- **Healthy threshold:** consecutive successes before marking back up (e.g., 2).

```nginx
# nginx Plus / OpenResty active health check example
upstream backend {
    zone backend_zone 64k;
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;

    # active health check (nginx Plus)
    # check interval=5000 rise=2 fall=3 timeout=3000 type=http;
    # check_http_send "GET /health HTTP/1.1\r\nHost: localhost\r\n\r\n";
    # check_http_expect_alive http_2xx;
}
```

In open-source nginx, passive health checks are configured with `max_fails` and `fail_timeout`:

```nginx
upstream backend {
    server 10.0.0.1:3000 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:3000 max_fails=3 fail_timeout=30s;
}
```

After 3 failures within 30 seconds, the server is considered down for 30 seconds before nginx retries.

### TLS Termination at the Load Balancer

TLS termination means the load balancer decrypts incoming HTTPS traffic and forwards plaintext HTTP to backends.

**Why do it:**
- Offloads CPU-intensive TLS handshakes from application servers.
- Centralizes certificate management (one place to rotate certs).
- Enables L7 inspection (you cannot read HTTP headers on encrypted traffic).

**Trade-offs:**
- Traffic between LB and backends is unencrypted -- acceptable inside a trusted network or VPC, unacceptable across the public internet.
- The LB must hold the private key -- a compromise of the LB exposes the key.
- For compliance (PCI-DSS, HIPAA), you may need re-encryption (TLS between LB and backends too).

### Sticky Sessions vs Stateless Design

| | Sticky Sessions | Stateless + External Store |
|---|---|---|
| **Mechanism** | Cookie or IP hash routes same client to same server | Session data in Redis/Memcached; any server can handle any request |
| **Server failure** | Client loses session (logged out, cart lost) | No impact -- next server reads from shared store |
| **Scaling** | Adding servers does not help existing sessions | Adding servers works immediately |
| **Complexity** | Simple to set up | Requires external store infrastructure |
| **Recommendation** | Legacy or quick prototyping only | **Strongly preferred for production** |

```nginx
# Sticky via cookie (nginx Plus)
upstream backend {
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    sticky cookie srv_id expires=1h path=/;
}
```

The stateless approach: store sessions in Redis, let the LB use `least_conn`, and never worry about server affinity.

## 💥 Where It Bites (Production Lens)

::: warning Where It Bites

**1. Hot servers from IP hash behind NAT**
*Symptoms:* One backend at 95% CPU, others idle. Alerts fire for latency spikes.
*Root cause:* A large corporate client sends all traffic from a single NAT IP. IP hash sends 100% of that traffic to one server.
*Diagnosis:* Check per-upstream connection counts (`nginx stub_status` or metrics). Switch to `least_conn` or use a header-based hash (e.g., `hash $http_x_request_id`) instead.

**2. Zombie servers passing TCP health checks**
*Symptoms:* Intermittent 502 errors even though all backends show as healthy.
*Root cause:* The Node.js process is stuck (event loop blocked, OOM but not crashed). TCP port is still open, so TCP health checks pass, but the app cannot respond to HTTP requests.
*Diagnosis:* Switch to HTTP health checks (`GET /health`) that exercise the application. Add a readiness endpoint that checks database connectivity and event loop lag.

**3. Session loss after deploy**
*Symptoms:* Users randomly logged out during rolling deploys.
*Root cause:* Sticky sessions via IP hash. When a server restarts during deploy, its clients are rehashed to another server that has no session data.
*Diagnosis:* Move to external session storage (Redis). If you must use sticky sessions short-term, implement session replication or graceful drain before shutdown.

**4. Least-connections thundering herd**
*Symptoms:* After a server recovers from downtime, it gets slammed with requests and immediately falls over again.
*Root cause:* The recovered server has 0 connections, so `least_conn` routes all new requests to it simultaneously.
*Diagnosis:* Use slow-start (ramp up weight gradually after recovery). In nginx Plus: `server 10.0.0.1:3000 slow_start=30s;`. In open-source nginx, manually adjust weights during recovery.
:::

## 🎯 Checkpoint

::: details Question 1 -- L4 vs L7 trade-off
**Q:** A service handles both HTTP API traffic and raw TCP connections for a custom binary protocol. You need path-based routing for the HTTP traffic. Can you use a single L7 load balancer for everything?

**A:** No. An L7 load balancer understands HTTP and can do path-based routing, but it cannot properly handle an arbitrary binary protocol over TCP -- it would try to parse the traffic as HTTP and fail. The correct approach is to use an L7 load balancer for the HTTP API traffic (with path-based routing) and a separate L4 load balancer for the custom TCP protocol. Some tools like HAProxy can run both an L4 frontend and an L7 frontend in the same process, but they are logically separate configurations.
:::

::: details Question 2 -- Algorithm selection
**Q:** You have a cluster of servers where 80% of requests complete in 5ms but 20% involve heavy computation and take 2 seconds. Round-robin is causing timeouts. Why, and what algorithm should you switch to?

**A:** Round-robin distributes requests evenly by count, ignoring how long each request takes. A server that receives several 2-second requests in a row accumulates a backlog while other servers sit idle. The fix is `least_conn` (least connections). It routes new requests to the server with the fewest in-flight connections, so servers stuck processing slow requests naturally stop receiving new ones until they catch up. This is the go-to algorithm for workloads with variable request duration.
:::

::: details Question 3 -- Consistent hashing
**Q:** You have 4 cache servers using consistent hashing. You add a 5th server. Roughly what fraction of cached keys will be invalidated (remapped)?

**A:** Approximately 1/5 (20%) of keys will be remapped to the new server. This is the key advantage of consistent hashing -- only ~1/n keys move when the n-th server is added, compared to modular hashing where nearly all keys would be reshuffled. With virtual nodes, the distribution is even more uniform, but the fraction remapped remains approximately 1/n.
:::

## 🏗️ Design It

::: details Scenario: Uneven CPU utilization across backends

**Problem:** You have 5 Node.js servers behind a load balancer. Monitoring shows servers 1 and 4 running at 90% CPU while servers 2, 3, and 5 sit at 20%. Users are reporting increased latency. What algorithm fixes this and why?

---

**Worked Solution:**

**Step 1 -- Identify the current algorithm.** The uneven distribution with some servers overloaded and others idle is a classic symptom of either round-robin with non-uniform request costs, or IP hash with skewed client distribution. Check the load balancer config.

**Step 2 -- Diagnose the root cause.** If the algorithm is round-robin, the likely cause is that requests routed to servers 1 and 4 happen to be computationally expensive (e.g., report generation, image processing) while other servers get lightweight requests. Round-robin does not account for how busy a server actually is. If the algorithm is IP hash, a few high-volume clients may be hashed to servers 1 and 4.

**Step 3 -- Switch to `least_conn`.** Least connections solves both root causes:
- It measures actual server load by counting active connections.
- Servers processing slow/heavy requests accumulate connections and stop receiving new ones.
- Servers that finish quickly stay at low connection counts and receive more work.

**Step 4 -- Implementation:**

```nginx
upstream node_app {
    least_conn;
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
    server 10.0.0.4:3000;
    server 10.0.0.5:3000;
}
```

**Step 5 -- Verify.** After deploying, monitor CPU utilization across all 5 servers. You should see convergence toward a similar utilization level (not identical, but within 10-15% of each other).

**Step 6 -- Consider further improvements.** If some servers have more CPU/memory than others, add weights: `server 10.0.0.1:3000 weight=2;`. If you need cache affinity, consider `consistent hash` with a fallback to least connections for non-cacheable requests.
:::

## Key Mental Models

- **L4 is fast but blind; L7 is smart but heavier.** Choose based on whether you need content-aware routing.
- **Least connections adapts to reality.** Unlike round-robin, it responds to actual server load, making it the default choice for most web workloads.
- **Consistent hashing protects caches during scaling.** Only ~1/n keys move when a server is added or removed.
- **Sticky sessions are a liability.** Server death means session death. Store state externally and let any server handle any request.
- **Health checks must test what matters.** A TCP connect proves the port is open; an HTTP health check proves the application is responsive.
