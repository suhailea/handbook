# System Design — 25 Interview Questions

25 curated questions covering message queues, microservices, load balancing, caching, and scaling. Each answer explains the trade-offs and reasoning, not just the pattern name.

---

## Message Queues

::: details Q1 — Why is exactly-once delivery "mostly a lie"?
**Q:** Distributed systems literature talks about at-most-once, at-least-once, and exactly-once delivery. Why do experienced engineers say exactly-once is "mostly a lie"?

**A:** True exactly-once delivery requires that the broker, the network, and the consumer all agree atomically that a message was produced, delivered, and processed — exactly one time. In practice, this is impossible across an unreliable network because the Two Generals Problem applies: the consumer may process the message and crash *before* acknowledging it, causing the broker to redeliver. What systems like Kafka Transactions actually provide is exactly-once *semantics* — at-least-once delivery combined with idempotent processing on the consumer side, so the *observable effect* appears to have happened once. This is a critical distinction: the message may physically be delivered more than once, but the system is designed so that duplicate deliveries produce no additional side effects. When someone sells you "exactly-once," ask whether they mean the transport guarantee (impossible without atomic broadcast) or the end-to-end semantic guarantee (achievable, but pushes complexity to the consumer via idempotency keys, deduplication tables, or transactional outboxes). The engineering cost of exactly-once semantics is real — it requires consumer-side state management, careful offset commits, and often a transactional store — so you should only pay that cost when duplicates cause actual business harm (double charges, duplicate notifications), not for every queue in the system.
:::

::: details Q2 — Kafka vs a simple Redis queue
**Q:** When should you reach for Kafka instead of a simple Redis-backed queue like BullMQ, and when is Kafka overkill?

**A:** Redis-backed queues (BullMQ, Bee-Queue) excel when you need job scheduling, delayed jobs, priorities, rate limiting, and relatively simple fan-out — all with minimal operational overhead and sub-millisecond latency for small payloads. They work well up to tens of thousands of messages per second on a single Redis instance. Kafka is designed for a fundamentally different use case: a durable, ordered, replayable commit log. Choose Kafka when you need multiple independent consumers reading the same stream of events at their own pace (consumer groups with independent offsets), when you need to replay history (a new service joins and needs to process the last 30 days of events), when ordering within a partition matters (event sourcing), or when throughput requirements reach hundreds of thousands to millions of messages per second. The cost of Kafka is real: you need ZooKeeper or KRaft, partition planning, consumer group rebalancing awareness, and operational expertise. For a typical web app that needs background job processing — sending emails, resizing images, generating reports — Redis queues are dramatically simpler and perfectly sufficient. The decision boundary is usually: "Do I need a job queue (Redis) or an event log (Kafka)?" If no consumer ever needs to re-read old messages, Kafka's core strength (the replayable log) is wasted.
:::

::: details Q3 — Idempotency keys for duplicate prevention
**Q:** How do idempotency keys prevent duplicate processing, and what are the implementation pitfalls?

**A:** An idempotency key is a unique identifier (typically a UUID or a deterministic hash of the request payload) that the producer attaches to each message. The consumer stores the key in a durable set (a database table or Redis SET) *within the same transaction* as the business operation. Before processing, the consumer checks the set — if the key exists, it skips processing and returns the cached result. The critical implementation detail is atomicity: the check-and-insert of the idempotency key *must* happen in the same transaction as the side effect. If you check the key, perform the work, and then insert the key as separate steps, a crash between the work and the insert causes a re-delivery that passes the idempotency check, producing a duplicate. Other pitfalls include: key expiration (you need a TTL strategy, but too-short TTLs reopen the duplicate window), storage growth (millions of keys need periodic cleanup), and the question of *who generates the key* — if the producer retries with a new key each time, idempotency is defeated. The producer must reuse the same key across retries. Finally, idempotency only protects against duplicate *processing* — if the upstream system sends two genuinely different requests that happen to have the same business meaning, idempotency keys won't help; you need domain-level deduplication.
:::

::: details Q4 — The transactional outbox pattern
**Q:** What is the transactional outbox pattern, and when do you actually need it?

**A:** The transactional outbox solves the dual-write problem: when a service needs to update its database *and* publish an event to a message broker, doing both atomically is impossible without a coordination protocol. If you write to the database and then publish, a crash between the two means the event is lost. If you publish first and then write, a crash means the database is inconsistent with the published event. The outbox pattern sidesteps this by writing the event to an "outbox" table in the *same database transaction* as the business data change. A separate process (a poller or a CDC connector like Debezium) reads the outbox table and publishes events to the broker, deleting or marking them as published afterward. Because the event and the data change share a single ACID transaction, they are guaranteed to be consistent. You need this pattern whenever event publishing must be reliable and consistent with database state — order placement events, payment state changes, inventory updates. You do *not* need it for best-effort notifications (like analytics events) where occasional loss is tolerable. The trade-off is added complexity: you now have an outbox table to manage, a relay process to operate and monitor, and at-least-once delivery semantics from the relay (since the relay might publish and crash before marking the row as sent), which means consumers still need idempotency handling.
:::

::: details Q5 — Exponential backoff with jitter
**Q:** How should you design an exponential backoff strategy with jitter, and what goes wrong without jitter?

**A:** Exponential backoff spaces out retries by doubling the delay each attempt — e.g., 1s, 2s, 4s, 8s — so that a failing downstream service gets breathing room to recover. Without jitter, every client that failed at the same moment retries at the *same* exponentially-backed-off times, creating synchronized "thundering herd" spikes that can re-crash the recovering service. Jitter randomizes the retry time within a window to spread the load. There are two common jitter strategies: "full jitter" picks a random delay between 0 and the exponential cap (`random(0, min(cap, base * 2^attempt))`), and "decorrelated jitter" uses the previous delay to compute the next (`delay = random(base, prev_delay * 3)`). AWS's research showed that full jitter produces the best spread and fewest total calls. Beyond jitter, a production implementation needs: a maximum retry count (not infinite), a maximum delay cap (e.g., 60s — don't let the exponent run away), dead-letter routing after exhausting retries, and per-error-type decisions (retry on 503/timeout, do *not* retry on 400/validation errors — those will never succeed). A subtle pitfall: if your backoff is per-request but the downstream failure is systemic, even jittered backoff may not help — you need a circuit breaker to stop sending requests entirely until the downstream recovers.
:::

## Microservices

::: details Q6 — Why start with a monolith?
**Q:** The "monolith-first" approach is widely recommended. Why, and when is it actually wrong?

**A:** A monolith gives you speed of iteration, simple deployments, straightforward debugging (one process, one stack trace), trivial data consistency (one database, real transactions), and dramatically lower operational overhead. In the early stages of a product, you do not yet know where the domain boundaries are — and microservices chosen along wrong boundaries are worse than a monolith because you pay the distributed-systems tax (network latency, partial failures, data consistency challenges, deployment coordination) without the benefit of independent scaling or team autonomy. The "monolith-first" approach lets you discover natural seam lines through real usage patterns, then extract services along those seams when there is a concrete reason: a component needs independent scaling, a team needs to deploy independently, or a module has fundamentally different reliability or technology requirements. The approach is *wrong* when you genuinely know the domain boundaries upfront (a rewrite of a system you already operate), when organizational structure demands independent team deployments from day one (Conway's Law in action), or when specific components have wildly different scaling profiles from the start (e.g., a real-time media transcoding pipeline vs. a CRUD API). But these cases are rarer than people think. The default should be: monolith until proven otherwise, with the discipline to keep internal module boundaries clean so extraction is possible later.
:::

::: details Q7 — gRPC over REST
**Q:** When would you choose gRPC over REST for inter-service communication, and when is REST the better choice?

**A:** gRPC excels in service-to-service communication where you control both ends: it uses HTTP/2 for multiplexed connections (reducing connection overhead), Protocol Buffers for compact binary serialization (smaller payloads, faster parsing than JSON — typically 5-10x), and code-generated clients/servers with strong typing that catch contract mismatches at compile time rather than runtime. It supports streaming in both directions (server-streaming, client-streaming, bidirectional), which is awkward to retrofit onto REST. Choose gRPC when latency and throughput matter (high-volume internal RPCs), when you want strict schema enforcement across many services, or when you need streaming. Choose REST when your API is public-facing (browsers speak HTTP/JSON natively, gRPC-Web is an extra layer), when human debuggability matters (you can `curl` a REST API, but not easily a gRPC one), when your team lacks gRPC operational experience (debugging, load balancing L7 gRPC, handling deadline propagation), or when the communication is simple request-response at low volume where the serialization savings are irrelevant. A common middle ground is gRPC for internal high-traffic service-to-service calls and REST/JSON for public APIs and low-frequency internal endpoints. Also note: gRPC load balancing is more complex because HTTP/2's persistent connections mean L4 balancers distribute connections, not requests — you often need client-side balancing or an L7-aware proxy.
:::

::: details Q8 — Saga pattern for distributed transactions
**Q:** How does the saga pattern handle distributed transactions, and what are the failure modes you must design for?

**A:** A saga replaces a single ACID transaction across multiple services with a sequence of local transactions, each paired with a *compensating action* that undoes its effect if a later step fails. For example, an order saga might: (1) reserve inventory, (2) charge payment, (3) create shipment. If step 3 fails, the saga runs compensating actions in reverse: refund payment, then release inventory. There are two coordination styles: *choreography* (each service publishes an event and the next service reacts — simple but hard to trace and reason about as sagas grow) and *orchestration* (a central orchestrator directs the steps — easier to understand and monitor but introduces a single point of coordination). The failure modes you must design for are substantial. Compensating actions can themselves fail, so they must be retryable and idempotent. Some actions are not easily compensable — you cannot "unsend" an email or "uncharge" a credit card (you issue a refund, which is a *new* action with its own failure modes). You must handle the case where a participant is unavailable to run its compensation. The saga provides no isolation — other transactions can see intermediate state (inventory reserved but payment not yet charged), which may require countermeasures like semantic locks. Sagas are significantly more complex than distributed transactions, so use them only when you genuinely cannot put the data in one database.
:::

::: details Q9 — Circuit breaker states
**Q:** What is a circuit breaker in microservices, and how do the three states (closed, open, half-open) work together?

**A:** A circuit breaker wraps calls to a downstream service and monitors failures. In the **closed** state (normal operation), requests pass through and failures are counted. When failures exceed a threshold within a time window (e.g., 50% of calls fail within 10 seconds), the breaker **trips to open**: all subsequent calls fail immediately without hitting the downstream service, returning a fallback or error. This prevents a failing service from being overwhelmed by retries and protects the calling service from wasting resources on calls that will likely fail (cascading failure prevention). After a configurable timeout, the breaker enters **half-open**: it allows a small number of probe requests through. If those succeed, the breaker resets to closed; if they fail, it returns to open for another timeout period. The design nuances that matter in production: choose your failure criteria carefully (timeouts, 5xx errors, connection refused — but not 4xx, which indicate client bugs, not service failure); tune the threshold and window to avoid flapping; ensure the half-open probe count is small enough to not re-overwhelm a recovering service; pair circuit breakers with fallback strategies (cached data, degraded responses, queue-for-later); and monitor breaker state as a first-class operational signal. A common mistake is setting the open-state timeout too short, so the breaker keeps probing a still-recovering service and never gives it time to heal.
:::

::: details Q10 — Preventing retry storms
**Q:** How do you prevent retry storms from cascading through a microservice architecture?

**A:** Retry storms happen when service A retries calls to service B, which is itself retrying calls to service C, creating a multiplicative explosion: if each layer retries 3 times, service C receives 3 x 3 = 9 requests for every original request from A. The first defense is **retry budgets**: instead of retrying a fixed number of times per request, track the ratio of retries to original requests across the service, and stop retrying when the ratio exceeds a threshold (e.g., 10% of traffic is retries). This caps the amplification factor. Second, **only retry at one layer** — typically the outermost caller. Intermediate services should propagate failures, not retry them. Third, use **deadline propagation**: pass a request deadline (absolute timestamp, not relative timeout) through the call chain so that downstream services can short-circuit immediately if the deadline has already passed, rather than doing work whose result will be discarded. Fourth, **circuit breakers** stop retries entirely when a downstream is unhealthy. Fifth, **backoff with jitter** on whatever retries remain ensures they do not synchronize. Sixth, distinguish retriable errors (503, timeout, connection reset) from non-retriable errors (400, 404, 409) and never retry the latter. A subtle anti-pattern: retry logic hidden inside client libraries at every layer — audit all layers to understand the total retry fan-out.
:::

## Load Balancing

::: details Q11 — L4 vs L7 load balancing
**Q:** When would you choose L4 (transport layer) over L7 (application layer) load balancing, and vice versa?

**A:** L4 load balancers route based on TCP/UDP connection metadata (source/destination IP and port) without inspecting the payload. They are fast, low-overhead, and protocol-agnostic — they work with any TCP traffic (databases, custom binary protocols, gRPC, game servers). L7 load balancers parse the application protocol (HTTP headers, URL paths, cookies) and can make routing decisions based on content: path-based routing (`/api` to one backend, `/static` to another), header-based routing (canary deployments by user-agent), cookie-based session affinity, and request-level health checking. Choose L4 when you need raw throughput and low latency, when you are balancing non-HTTP protocols, or when the overhead of HTTP parsing is unacceptable. Choose L7 when you need content-aware routing, TLS termination at the balancer, HTTP-specific features (compression, header injection, request/response transformation), or per-request distribution (L4 distributes *connections*, not *requests* — with HTTP/2 and long-lived connections, L4 can produce severe imbalance). Most modern web architectures use L7 (nginx, HAProxy in HTTP mode, AWS ALB) because the routing flexibility and per-request distribution outweigh the small parsing overhead. A common pattern is L4 at the edge (for TCP pass-through or UDP) with L7 internally for HTTP services.
:::

::: details Q12 — nginx buffering and SSE streaming
**Q:** Why does nginx's default buffering behavior break Server-Sent Events (SSE) streaming, and how do you fix it?

**A:** By default, nginx buffers the upstream response body: it reads the full response (or chunks up to `proxy_buffering`'s buffer size) from the backend before forwarding it to the client. This is normally desirable — it frees the backend connection quickly and absorbs slow clients. But SSE is a long-lived HTTP response where the server sends events incrementally over minutes or hours. With buffering on, nginx holds the first batch of events in its buffer and does not flush them to the client until the buffer fills or the connection closes, causing the client to see long delays or no data at all. The fix is `proxy_buffering off;` in the relevant location block, which tells nginx to forward each chunk from the backend to the client immediately. You should also set `proxy_cache off;` (caching a stream is meaningless), `proxy_read_timeout` to a high value (so nginx does not close the long-lived connection for inactivity), and include the headers `X-Accel-Buffering: no` from the backend as a per-response override. For LLM token streaming, this is a must-have configuration — without it, users see tokens arrive in large delayed batches instead of one-by-one, destroying the streaming UX. Also set `proxy_http_version 1.1;` and `proxy_set_header Connection "";` to enable keepalive to the upstream, since SSE over HTTP/1.0 does not support chunked transfer encoding.
:::

::: details Q13 — nginx `keepalive` directive in upstream blocks
**Q:** What does the `keepalive` directive in an nginx `upstream` block actually control, and what happens when you get it wrong?

**A:** The `keepalive` directive sets the maximum number of *idle* keep-alive connections to upstream servers that are cached *per worker process*. It does not limit the total number of connections — it limits how many idle connections nginx keeps open in a pool for reuse. When a proxied request completes, instead of closing the TCP connection to the backend, nginx puts it back in the pool (up to the `keepalive` limit). The next request to that upstream reuses the pooled connection, avoiding TCP handshake and TLS negotiation overhead. If you set it too low (or omit it), nginx opens a new TCP connection for every request, which under load means thousands of connections in TIME_WAIT state on both nginx and backend, port exhaustion, and elevated latency from repeated handshakes. If you set it too high, you hold open many idle connections consuming file descriptors on both sides. A good starting point is 2x the expected concurrent requests per worker to that upstream. Critically, `keepalive` only works if you also set `proxy_http_version 1.1;` and `proxy_set_header Connection "";` in the location block — without these, nginx uses HTTP/1.0 with `Connection: close` by default, which closes the connection after every request, making the keepalive pool useless. This is one of the most common nginx misconfigurations in production.
:::

::: details Q14 — Least-connections vs round-robin
**Q:** When would you choose least-connections over round-robin load balancing?

**A:** Round-robin assigns requests cyclically regardless of how busy each backend is. It works well when requests have roughly uniform cost (similar response times and resource consumption) and backends have identical capacity. It fails when request costs vary widely — a backend that receives a few slow requests (large file uploads, complex database queries, LLM inference) accumulates a backlog while round-robin keeps sending it the same rate of new requests as every other backend. Least-connections routes each new request to the backend with the fewest active (in-flight) connections, which naturally adapts to heterogeneous request costs: slow backends accumulate connections and receive fewer new requests, fast backends drain their connections and receive more. Choose least-connections when request durations vary significantly, when backends have different capacities (e.g., during a rolling deploy where old and new instance types coexist), or when you observe uneven latency percentiles across backends despite round-robin. The trade-off: least-connections requires tracking per-backend connection counts, which adds minimal overhead but means the balancer must be stateful per-connection. For the weighted variant (`least_conn` with `weight` in nginx), you can express capacity differences explicitly. A subtlety: if backends are behind a connection pool (e.g., a sidecar proxy), the balancer sees pool connections, not real request load, which can defeat least-connections — inspect what the balancer actually counts.
:::

::: details Q15 — Proxying WebSocket connections through nginx
**Q:** How do you configure nginx to proxy WebSocket connections, and what breaks if you miss a step?

**A:** WebSocket connections start as an HTTP/1.1 request with `Upgrade: websocket` and `Connection: Upgrade` headers. The server responds with `101 Switching Protocols`, and the connection is then upgraded to a persistent, full-duplex TCP channel. Nginx can proxy this, but you must explicitly forward the hop-by-hop headers that HTTP proxies normally strip: `proxy_set_header Upgrade $http_upgrade;` and `proxy_set_header Connection "upgrade";`. You also need `proxy_http_version 1.1;` because HTTP/1.0 does not support connection upgrades. Without the `Upgrade` header forwarding, the backend never sees the upgrade request, returns a normal HTTP response, and the WebSocket handshake fails — the client typically receives a 400 or 200 instead of 101. Without `proxy_http_version 1.1`, nginx sends the request as HTTP/1.0, which does not support the `Upgrade` mechanism. Additionally, set `proxy_read_timeout` to a high value (e.g., 3600s) or rely on WebSocket-level pings, because nginx's default 60-second read timeout will close idle WebSocket connections that have no traffic. A production consideration: if you use `keepalive` in the upstream block, WebSocket connections consume a slot for their entire lifetime (they are never "idle and returned to the pool"), so size your keepalive pool for non-WebSocket traffic separately.
:::

## Caching

::: details Q16 — Cache stampede and prevention
**Q:** What is a cache stampede and what are the main strategies to prevent it?

**A:** A cache stampede (also called "thundering herd on cache miss") occurs when a popular cache key expires and many concurrent requests simultaneously see the miss, all hit the database to regenerate the value, and then all write it back to cache. For hot keys, this can mean thousands of identical expensive queries hitting the database in the span of milliseconds, potentially overwhelming it. Prevention strategies: (1) **Single-flight / request coalescing**: only the first request on a cache miss actually queries the database; concurrent requests for the same key wait for the first one to finish and then share the result. This is the most effective approach and can be implemented with a distributed lock (e.g., Redis `SET NX` with a short TTL) or in-process deduplication. (2) **Staggered TTLs with jitter**: instead of all keys expiring at exactly the same time, add a random offset (e.g., TTL = base + random(0, 60s)) so expirations spread out. (3) **Background refresh / early recomputation**: track when a key is "about to expire" (e.g., at 80% of TTL) and proactively regenerate it in the background before it actually expires, so no request ever sees a miss. (4) **Lock-and-recompute**: on a miss, acquire a short-lived lock; if the lock is already held, return stale data (if available) or wait. Each strategy has trade-offs: single-flight adds latency for waiters, jitter does not prevent stampede on a single hot key, and background refresh adds infrastructure complexity.
:::

::: details Q17 — Cache-aside vs write-through
**Q:** When would you use a cache-aside pattern versus write-through, and what are the consistency implications of each?

**A:** In **cache-aside** (also called "lazy loading"), the application is responsible for cache management: on a read, check the cache first; on a miss, query the database, write the result to cache, and return it. On a write, update the database and invalidate (or delete) the cache entry. The advantage is simplicity and the fact that you only cache data that is actually read — no wasted cache space on unread data. The disadvantage is that after a write, the next read always misses (briefly inconsistent or slower). In **write-through**, every write goes to the cache and the database simultaneously (or the cache write triggers the database write). Reads always hit the cache and are fast. The advantage is that cache and database are more closely synchronized, and reads after writes are immediate cache hits. The disadvantage is write latency (every write pays the cache write cost even if the data is never read) and wasted cache space for write-heavy, read-light data. Use cache-aside when reads vastly outnumber writes and you want to keep caching simple and opt-in. Use write-through when read-after-write consistency matters (e.g., user profile updates that are immediately re-read) and you can tolerate the write overhead. A third option, **write-behind** (write to cache immediately, asynchronously flush to database), improves write latency but risks data loss if the cache crashes before flushing — suitable only when that risk is acceptable.
:::

::: details Q18 — Redis eviction policies
**Q:** How does Redis eviction work and which policy should you choose?

**A:** When Redis reaches its `maxmemory` limit, it must evict keys to make room for new writes. The eviction policy, configured via `maxmemory-policy`, determines which keys are candidates. The main policies: **noeviction** rejects new writes (returns errors) — use when data loss is unacceptable and you would rather fail than silently lose data. **allkeys-lru** evicts the least recently used key from the entire keyspace — the best general-purpose choice for caching, where any key can be regenerated from the source. **volatile-lru** evicts the least recently used key *only among keys with a TTL set* — use when you mix cache data (with TTLs) and persistent data (without TTLs) in the same instance and want to protect the persistent data. **allkeys-lfu** (since Redis 4.0) evicts the *least frequently* used key — better than LRU when access patterns are skewed (a few very hot keys should be protected even if not accessed in the last few seconds). **allkeys-random** evicts a random key — occasionally useful when access patterns are truly uniform and the overhead of tracking LRU/LFU metadata matters. The common mistake is leaving the default `noeviction` on a cache instance, which causes write errors when memory fills up instead of gracefully evicting cold data. For most caching use cases, `allkeys-lru` or `allkeys-lfu` is the right choice. For mixed-use Redis (cache + queues + pub/sub), consider `volatile-lru` so non-TTL keys used for queues are never evicted — or, better yet, separate your cache Redis from your data Redis.
:::

::: details Q19 — CDN caching vs application-level caching
**Q:** What are the trade-offs of CDN caching versus application-level caching?

**A:** CDN caching (Cloudflare, CloudFront, Fastly) places cached responses at edge nodes geographically close to users, reducing latency by avoiding the round trip to your origin server. It excels for static assets, public API responses, and content that is identical for all users. The trade-offs: you lose fine-grained control over invalidation (CDN purge APIs have propagation delays, typically seconds to minutes across all edge nodes), cache keys are usually limited to URL + a few headers (complex vary-by-user-role logic is awkward), and you are caching at the HTTP layer so the entire response must be cacheable (no partial caching of expensive sub-computations). Application-level caching (Redis, in-process LRU) sits in your infrastructure, close to your data sources. It can cache arbitrary computation results (a complex aggregation, a joined query result, a serialized object), vary by any application-level key (user ID, tenant, feature flags), and be invalidated instantly and precisely. The trade-off is that it does not reduce network latency for geographically distant users and adds infrastructure to manage. The ideal approach layers both: CDN at the edge for public, static, and semi-static content (with appropriate `Cache-Control` headers), and application-level caching behind the CDN for personalized or computed data. A common mistake is CDN-caching responses that include user-specific data (authentication tokens, personalized content) — this leaks private data to other users and is a severe security vulnerability.
:::

::: details Q20 — Cache invalidation without stampedes
**Q:** How do you invalidate caches without causing stampedes?

**A:** The naive approach — delete the cache key on data change — is correct for consistency but creates a stampede window: between the deletion and the first successful recomputation, every concurrent request sees a miss and hits the database. Strategies to invalidate safely: (1) **Replace, don't delete**: instead of deleting the key, write the new value directly to the cache in the same operation that updates the database (write-through on mutation). This way there is no miss window — readers see the old value and then the new value, never a miss. This only works when the writing code path can compute the cached representation. (2) **Stale-while-revalidate**: serve the stale (old) cached value to readers while a single background process recomputes the new value. The `SWR` pattern (or HTTP `stale-while-revalidate` directive) makes this explicit: the cache entry has a "stale" TTL beyond its "fresh" TTL, during which it is served but triggers a background refresh. (3) **Probabilistic early expiration**: each reader, upon accessing a cache entry, rolls a die based on how close the entry is to expiration. The closer to expiry, the higher the probability of triggering an early recompute — statistically, exactly one reader refreshes the entry before it actually expires. (4) **Versioned keys**: instead of invalidating a key, change the key itself (e.g., `user:42:v3` → `user:42:v4`). Old keys expire naturally via TTL. This eliminates explicit invalidation entirely but requires propagating the version number. The best approach depends on how stale your data can be and how expensive the recomputation is — for cheap recomputes, simple delete-and-refill with single-flight protection is fine; for expensive ones, stale-while-revalidate prevents latency spikes.
:::

## Scaling

::: details Q21 — Statelessness and horizontal scaling
**Q:** What makes a service "stateless" and why does horizontal scaling require it?

**A:** A stateless service stores no request-specific data in the process between requests — every request contains (or can retrieve from shared storage) everything needed to process it. This means any instance of the service can handle any request, and instances can be added or removed without coordination or data migration. Horizontal scaling (adding more instances) requires this property because a load balancer distributes requests arbitrarily across instances — if instance A holds session state from a user's previous request, but instance B receives the next request, the session is lost. The things that make a service stateful and must be externalized: in-memory sessions (move to Redis or JWTs), local file storage (move to S3 or a shared filesystem), in-process caches that assume consistency (move to Redis or accept eventual consistency), and WebSocket connection state (requires sticky sessions or a pub/sub backplane like Redis for cross-instance message delivery). Note that "stateless" does not mean the service has no state — it means the state lives in external stores (databases, caches, object storage) that all instances share. The cost of statelessness is latency to those external stores and the operational overhead of running them. A service with a large in-memory cache can technically be stateless (the cache is just an optimization, not required state) as long as it functions correctly with a cold cache on any fresh instance.
:::

::: details Q22 — Token bucket algorithm for rate limiting
**Q:** How does the token bucket algorithm work for rate limiting, and how would you implement it with Redis?

**A:** The token bucket maintains a bucket of tokens with a maximum capacity. Tokens are added at a fixed rate (e.g., 10 per second). Each request consumes one token. If the bucket is empty, the request is rejected (or queued). This allows bursts up to the bucket capacity while enforcing an average rate equal to the refill rate. For example, a bucket with capacity 100 and refill rate 10/s allows a burst of 100 requests instantly, but then only 10/s sustained. The Redis implementation uses a single key per rate-limit subject (e.g., `ratelimit:{user_id}`) storing the token count and last refill timestamp. On each request: (1) compute elapsed time since last refill, (2) add `elapsed * refill_rate` tokens (capped at capacity), (3) if tokens >= 1, decrement by 1 and allow the request, else reject. Steps 1-3 must be atomic — use a Lua script (`EVAL`) to avoid race conditions from concurrent requests. The alternative is a sliding window counter (using sorted sets or multiple time-bucketed counters), which gives smoother rate enforcement but is more expensive per-request in Redis operations. Token bucket is preferred when you want to explicitly allow bursts (API rate limits where the user accumulates "credit" during idle periods). Sliding window log (sorted set of timestamps) is preferred when you want strict "no more than N requests in any X-second window" enforcement. The trade-off: token bucket is O(1) per request in Redis, sliding window log is O(N) where N is the window size.
:::

::: details Q23 — Sharding vs read replicas
**Q:** When should you shard a database versus add read replicas?

**A:** Read replicas solve a *read throughput* problem: if your database is overwhelmed by queries but write volume is manageable, replicate the data to read-only copies and distribute read traffic across them. The primary handles all writes, replicas asynchronously (or semi-synchronously) replicate and serve reads. This is operationally simple, does not require application-level data partitioning, and works well when the read-to-write ratio is high (10:1 or more). Sharding (horizontal partitioning) solves a *write throughput or data size* problem: when a single node cannot handle the write volume, or the dataset exceeds what one machine can store, you split data across multiple independent databases by a shard key (e.g., user_id modulo N). Each shard handles reads and writes for its partition. Sharding is dramatically more complex: you must choose a shard key that distributes load evenly (hot shards defeat the purpose), cross-shard queries and joins become expensive or impossible, transactions across shards require distributed coordination, and rebalancing (adding shards) requires data migration. Start with read replicas — they handle most scaling needs with minimal complexity. Shard only when: (1) write volume exceeds a single node's capacity, (2) the dataset no longer fits on one machine, or (3) you need write-level isolation between tenants. A common hybrid: shard for writes, and each shard has its own read replicas. Also consider whether your actual bottleneck is the database at all — often caching, query optimization, or connection pooling solve the problem before you need to shard.
:::

::: details Q24 — Kubernetes HPA scaling decisions
**Q:** How does Kubernetes Horizontal Pod Autoscaler (HPA) decide when to scale, and what are the common pitfalls?

**A:** HPA periodically (default every 15 seconds) queries metrics and computes the desired replica count using the formula: `desiredReplicas = ceil(currentReplicas * (currentMetricValue / targetMetricValue))`. For example, if you target 50% CPU utilization, currently have 4 replicas, and average CPU is 75%, HPA computes `ceil(4 * 75/50) = 6` replicas. It supports CPU, memory, custom metrics (e.g., queue depth via Prometheus adapter), and external metrics. Common pitfalls: (1) **Scaling on memory is usually wrong** — memory usage tends to grow monotonically (heap, caches) and does not correlate with request load, causing HPA to scale up but never down. CPU or request rate are better proxies for load. (2) **Startup latency causes oscillation**: HPA scales up, new pods are not ready yet (pulling images, warming caches, establishing connections), so metrics stay bad, HPA scales up again, then all pods come online simultaneously and the system is over-provisioned. Mitigation: set `stabilizationWindowSeconds` and use `behavior` policies to limit scale-up rate. (3) **JVM/Node.js warm-up**: freshly started pods may report high CPU during JIT compilation or module loading, triggering premature scale-up. Use readiness probes that delay traffic until the pod is warm. (4) **Missing resource requests**: HPA cannot compute CPU percentage without `resources.requests.cpu` set on the container — it silently fails to scale. (5) **Scaling to zero** is not supported by default HPA (KEDA fills this gap for event-driven workloads). The best practice is to scale on a business-meaningful metric (requests per second, queue depth) rather than resource utilization, and to set both `minReplicas` and `maxReplicas` thoughtfully.
:::

::: details Q25 — Vertical vs horizontal scaling trade-offs
**Q:** What is the real difference between vertical and horizontal scaling trade-offs, beyond "bigger machine vs more machines"?

**A:** Vertical scaling (scaling up) means upgrading a single machine's resources: more CPU cores, more RAM, faster disks. Its advantages are simplicity — no application changes, no distributed-systems complexity, no data partitioning — and it works for inherently single-threaded or hard-to-parallelize workloads (a relational database primary, a single-threaded event loop). Its limits are hard: there is a maximum machine size (cloud providers cap at ~448 vCPUs / 24TB RAM as of 2025), cost scales super-linearly (a machine with 2x the resources costs more than 2x the price), and it creates a single point of failure with no redundancy. Horizontal scaling (scaling out) means adding more machines behind a load balancer. It requires the application to be stateless (or have externalized state), adds complexity (networking, service discovery, distributed consistency, deployment orchestration), but offers near-linear cost scaling, built-in redundancy (one instance failing does not take down the service), and theoretically unlimited capacity. The real decision framework: vertical scaling is your first move for databases and stateful workloads because distributing state is the hardest problem in distributed systems. Horizontal scaling is your first move for stateless compute (API servers, workers) because it is straightforward and gives you fault tolerance as a free side effect. In practice, most production systems use both: vertically scale the database as far as reasonable while horizontally scaling stateless application tiers, and shard the database only when vertical limits are hit. Never horizontally scale to avoid diagnosing a performance problem — if one instance cannot handle 100 requests per second and you just add instances, you are paying 10x for a problem that might be a missing index or an N+1 query.
:::
